# Правила структуры интеграционных сервисов(в том числе viva)

## 1. `instance.go` — handlers и middleware

В `instance.go` держим только:

- структуру основного сервиса;
- подключение handlers;
- подписки на HTTP/NATS/SMPP routes;
- middleware;
- thin handlers, если они только парсят request и вызывают сценарий.

В `instance.go` не держим бизнес-логику сценариев.

## 2. Сервисы по направлениям — отдельные файлы

Логику конкретного направления выносим в отдельный файл:

- `landing.go` — сценарии лендинга;
- `ussd.go` — MO/USSD сценарии;
- `order.go` — работа с заказами;
- `notify.go` — отправка уведомлений;
- `catalog.go` — каталог и шаблоны.

Сценарий — это линейная последовательность вызовов примитивов.

## 3. Вспомогательный функционал — отдельные файлы или пакеты

Повторяемый или самостоятельный функционал выносим отдельно:

- `langstore.go` — хранение языка;
- `log.go` — логирование ошибок;
- `catalog.go` — загрузка и поиск продуктов;
- отдельный пакет — если функционал переиспользуется между сервисами.

Не добавляем лишние абстракции заранее.

## 4. `types.go` — DTO и общие типы

В `types.go` держим:

- request/response DTO;
- общие структуры;
- типы, которые используются несколькими файлами.

В `types.go` не держим бизнес-логику.

## Общий принцип

Handler принимает запрос и вызывает сценарий.

Сценарий вызывает примитивы в нужном порядке.

Примитив делает одну конкретную операцию.

Пример:

```text
Transport → Handler → Scenario → Primitive → External service / Notify
```
